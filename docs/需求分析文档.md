## 1. 项目概述

### 1.1 产品定义

| 项 | 内容 |
|---|---|
| 产品名称 | 布谷（Cuckoo） |
| 产品类型 | 智能提醒与健康管理社交 Web PWA（可安装到手机桌面） |
| 核心定位 | 以精准定时提醒为基础，融合用药管理、短时锻炼、生活习惯养成与社交激励 |
| Slogan | 准时提醒，温柔守护——布谷，你的健康生活管家 |
| 核心闭环 | 提醒 → 执行 → 记录 → 激励 |
| 本期目标平台 | 移动端优先的 Web PWA（后续可扩展原生 App，后端完全复用） |

### 1.2 本期实现范围（正式产品标准）

- **P0 全量**：智能提醒系统、用药管理、喝水/作息/番茄钟、基础统计、用户系统
- **P1 全量**：拍照打卡挑战、短时锻炼（微运动库）、社交（帖子/点赞/评论/收藏/一键加入计划/小组）、周报月报、热力图、成就系统、亲友通知
- **P2 预留接口**：智能建议（推荐引擎接口预留）、数据导出、短信通知（SMS 提供商抽象层预留）、主题皮肤（Design Token 化，便于扩展）

### 1.3 与原始需求文档的主要差异（改进记录）

| # | 原文档 | 本版处理 | 理由 |
|---|---|---|---|
| 1 | "本地为主，定期与后端同步" | 明确**冲突解决策略**：以 updatedAt 为准的 last-write-wins + 软删除 + 服务端权威漏服判定 | 原表述无法实现多端一致性 |
| 2 | 漏服判定"本地可先做简单实现" | 漏服判定**仅后端权威执行**（App 被杀/离线时本地无法判定） | 本地判定在页面关闭时不可靠 |
| 3 | 无通知记录 | 新增 **NotificationLog** 实体，通知去重 + 发送记录 | 避免亲友重复收到通知、可追溯 |
| 4 | 成就类型枚举固定 | 成就改为**规则表驱动**（可配置阈值/名称/图标） | 运营可扩展成就，不改代码 |
| 5 | 计划分享仅贴 JSON 快照 | 新增 **PlanTemplate**（官方计划）+ 快照版本号，支持官方计划运营 | 官方计划与用户分享分离管理 |
| 6 | 无统计口径定义 | 明确定义完成率、连续天数、漏服判定窗口等**计算口径**（见 §6.3） | 避免前后端统计不一致 |
| 7 | 亲友通知依赖手机号 | 手机号需**验证码绑定**（P2 短信集成前支持 App 内验证/好友邀请码） | 防止骚扰他人 |
| 8 | 无内容治理 | 新增敏感词过滤、健康免责声明、举报机制（P1 简化版） | 健康类内容合规要求 |
| 9 | 无 API 规范 | 统一错误码、分页、幂等键、限流、审核字段 | 正式产品标准 |
| 10 | 平台仅 iOS/Android | 本期为 **Web PWA**（环境约束），原生端规划复用同一后端 | 见技术方案 |

## 2. 用户与场景

### 2.1 目标用户

| 用户群 | 核心诉求 | 关键功能 |
|---|---|---|
| 长期用药慢病患者 | 按时服药、库存不中断、家人监督 | 用药管理、库存预警、亲友通知、服药历史 |
| 久坐办公人群 | 起身活动、缓解肩颈/眼部疲劳 | 久坐提醒、微运动库、眼部放松、番茄钟 |
| 习惯养成用户 | 坚持喝水、规律作息 | 喝水提醒、作息提醒、连续天数、成就 |
| 社交激励用户 | 找到同伴、获得认可 | 计划分享、一键加入、小组、排行榜、成就墙 |

### 2.2 典型场景

1. **用药闭环**：用户设置每日服药提醒 → 到点弹窗展示药品照片+剂量 → 拍照打卡确认 → 自动扣减库存 → 库存低于阈值时通知本人+亲友；超 30 分钟未确认判定漏服 → 通知亲友。
2. **久坐纠正**：每 45 分钟提醒起身，附 30 秒拉伸视频；2 小时提醒颈部后缩动作。
3. **计划社交**：用户把喝水计划分享到社区 → 好友一键加入（可先预览修改）→ 帖子实时显示"XX 人已加入"。
4. **数据反馈**：周一查看周报（完成率、分类对比、下周建议）；月末查看热力图与成就总结。

### 2.3 用户旅程（注册 → 活跃 → 留存）

首次注册选择健康目标 → 生成个性化计划模板（一键启用）→ 日常提醒执行 → 数据看板反馈 → 达成成就 → 分享/加入社区 → 周报月报复购式回流。

## 6. 关键规则与计算口径（重要完善项）

### 6.1 完成率口径

- `当日完成率 = 完成数 ÷ 当日应执行数`，分母 = 计划数 − 跳过数（跳过不计入分母，但计入"跳过"统计）
- 延迟后再完成 → 按完成计，`平均延迟时长`纳入统计
- 漏服 = 未完成（计入分母）

### 6.2 连续天数口径

- 连续天数 = 从今天（或昨天，今天未执行完）向前回溯，**每天所有应执行提醒全部完成**（无跳过无漏服）的最大连续天数
- 今天的判定在当天 23:59 后冻结；当天未到 23:59 时，若今天已全部完成则计入
- 时区按用户设置时区计算（默认浏览器时区）

### 6.3 漏服判定口径

- 提醒触发后，超过 `missedThresholdMinutes`（默认 30）未完成/未延迟/未跳过 → 状态置 missed
- **延迟中的提醒不判定漏服**（延迟是已响应的操作）；延迟后再错过同样判定
- 判定由后端定时扫描执行（页面关闭也有效），App 端启动时拉取同步

### 6.4 边界情况规则

| 场景 | 规则 |
|---|---|
| 每月 31 日提醒，遇到 2 月 | 顺延到该月最后一天 |
| 自定义间隔（每 N 天）跨时区 | 按用户时区计算基准日 |
| 时区变更 | 提醒以新时区的绝对本地时间重新计算，变更时提示用户 |
| 提醒过期（设备离线错过） | 标记 missed，不补触发（除延迟操作） |
| 夏令时 | 按本地时间调度，忽略夏令时偏移 |
| 重复提醒创建后修改 | 修改生效于下一触发周期，不追溯历史 |
| 删除药品 | 关联用药提醒保留但解除药品关联（记录保留 medicineName 快照） |
| 加入计划后原帖删除 | 已加入用户的提醒不受影响（快照已复制） |

### 6.5 库存扣减规则

- 扣减时机：完成（含拍照挑战完成）时在同一数据库事务内执行：写入 ReminderLog + 更新 Medicine.stock + 写库存预警判定
- 扣减量取 `deductionPerUse`（默认 1）；PRN 手动记录同样走扣减流程
- 库存为 0 时：提醒仍可完成（记录但不扣减为负），预警通知置为"库存为 0，请及时补充"

## 9. 风险与依赖

| 风险 | 影响 | 应对 |
|---|---|---|
| Web Push 在部分浏览器/网络环境不可达 | 页面关闭时提醒丢失 | 双通道（页面打开时本地调度为主）；通知到达率埋点监控 |
| 用户拒绝通知权限 | 核心价值受损 | 引导页说明价值 + 权限降级提示（站内红点） |
| 健康数据敏感 | 合规与信任风险 | 最小化收集、HTTPS、隐私政策、数据导出删除 |
| 内容审核成本 | 社区内容合规风险 | 敏感词库 + 举报 + 官方计划人工审核 |
| 视觉评审不可用 | 评审流程受阻（沿用旧 ARK 脚本已废弃，评审依赖运行中多模态模型直接读图） | 使用内置多模态视觉评审（.zcode/skills/ui-review），无外部 API 依赖与成本 |
| 内容素材（微运动 50+） | P1 内容量不达标 | 种子 10+ 套上线，后续运营补充 |
